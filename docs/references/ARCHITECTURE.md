# ソフトウェアアーキテクチャ設計方針

## 概要

* DDD、Layered Architecture、Clean Architectureの思想を取り入れながら、本プロジェクトが従うソフトウェアアーキテクチャの設計方針を記します。
* 本プロジェクトに合った方法論を定めることを目的としており、上記の各概念で提唱されているアプローチとは必ずしも一致しないことにご注意ください。
* 本プロジェクトは、マルチエージェントシステムを活用したスタートアップ企業の意思決定支援アプリケーションのプロトタイプです。ターミナルを通じた処理が中心となります。
* プロンプトや設定値の変更による成果物の変化を検証することを主目的としています。

## レイヤー別のコンポーネント定義

### レイヤー構成

* ソフトウェアを構成する各コンポーネントは、以下の３つのレイヤーのいずれかに属します。

| レイヤー名 | 説明 |
| --- | --- |
| プレゼンテーション | 外部へのインタフェースを提供するレイヤー（アプリケーション仕様を実装）。本プロジェクトではCLIがプレゼンテーションの主体となる。 |
| ドメイン | アプリケーション仕様に依存しない純粋なビジネスロジックを記述するレイヤー。具体的なデータストレージやエージェントフレームワークに依存するコードはなく、十分抽象化され、かつ汎用性の高いコードを配備する。|
| データ | 具体的なデータソースやエージェントフレームワークに依存したコードを記述するレイヤー。 |

### レイヤー別のコンポーネント

* 各レイヤーに配備するコンポーネントは、以下のようになります。

| レイヤー名 | コンポーネント | 説明 |
| --- | --- | --- |
| プレゼンテーション | scripts | CLIのエントリポイントに相当。ターミナルから実行されるコマンドスクリプト。 |
| プレゼンテーション | usecases | scriptsから呼ばれることを想定した特定ユースケースのオーケストレーション（ただし、scripts間で共有する等の多少の汎用性を意識）。限定的なアプリケーション仕様はここで吸収され、汎用的な下位のレイヤーのコンポーネントを利用する。 |
| ドメイン | agents (interfaces) | エージェントの振る舞いを定義するインタフェース。具体的なエージェントフレームワーク（Google ADK等）には依存しない。下位のデータレイヤーにあるエージェント実装が準拠するべきインタフェースを定義する。 |
| ドメイン | services | エージェントやリポジトリ等を組み合わせて、複雑なロジックを表現するクラス。このクラスは、アプリケーション仕様に影響されない、十分汎用的なインタフェースを提供し、ユニットテストもしやすい設計にする。 |
| ドメイン | repositories (interfaces) | 下位のデータレイヤーにある repositories が実装するべきインタフェースを定義。 |
| ドメイン | entities | 各リポジトリが取扱う、抽象化されたデータ単位を表現。データソースには依存しない。 |
| データ | gateways | 外部システムの仕様を表現するゲートウェイとなるクラス。対象となる外部サービスの仕様はこのクラスで全て吸収する。外部仕様と内部仕様の変換については、domain/services が担当する。エージェントフレームワーク（Google ADK等）の具象実装もここに配備し、ドメインレイヤーの agents interface に準拠する。 |
| データ | repositories | データソースのデータの永続化や参照を担当するクラス。上位レイヤーの repositories interface に準拠したインタフェースを提供。 |
| データ | models | 外部ストレージのレコードを表現するモデルクラス。 |

### 依存関係の原則

* services は、agents や repositories を利用する際、同ドメインレイヤーで定義されるインタフェースを実装したインスタンスがDIにより注入されるようにする。そのようにすることで、動的に注入するインスタンスが解決され、service クラス自体はデータレイヤーのコードに一切依存しないようにする。
* 例えば、エージェントフレームワークを Google ADK から LangGraph 等に切り替える場合でも、ドメインレイヤー以上のコードは変更不要となる。

### ディレクトリ構成

* ディレクトリ構成は、以下のようになります。

```
+ src/
    + presentation/: プレゼンテーションレイヤー
        + scripts/: CLIエントリポイント
        + usecases/: ユースケース
    + domain/: ドメインレイヤー
        + agents/: エージェントのインタフェース定義
        + services/: 汎用ビジネスロジック
        + repositories/: リポジトリのインタフェース定義
        + entities/: データエンティティ
    + data/: データレイヤー
        + gateways/: 外部サービス連携
            + google_adk/: Google ADK に依存したコード
                + agents/: ADKエージェントの具象実装
        + repositories/: リポジトリの具象実装
        + models/: データモデル
    + tests/: テストコード
+ configs/
    + teams/: チーム定義（メンバー構成・プロンプト・トポロジーを一元管理するYAMLファイル）
+ docs/: 仕様書やドキュメント
+ outputs/: エージェントの議論結果レポートの出力先
```

### エージェントフレームワークの拡張

* 将来的に複数のエージェントフレームワークを比較検証する場合、データレイヤーにフレームワーク別のディレクトリを追加する。

```
+ src/
    + data/
        + gateways/
            + google_adk/: Google ADK 依存のコード
                + agents/
            + lang_graph/: LangGraph 依存のコード
                + agents/
            + microsoft_autogen/: Microsoft AutoGen 依存のコード
                + agents/
```

* いずれの実装も domain/agents で定義されたインタフェースに準拠することで、上位レイヤーからは統一的に利用できる。

### 検討項目

* gateways が返す外部仕様を表現するインスタンスと、内部で扱うインスタンスの変換が複雑化した場合、domain/services に担当させるのではなく、domain/adapters のような専用のクラスを配備。

## 設定管理ポリシー

### 変数定義方法の分類

アプリケーション設定は、性質に応じて以下の3つに分類し、適切な管理方法を選択する:

| 分類 | 管理方法 | 例 | 理由 |
| --- | --- | --- | --- |
| **機密情報** | 環境変数のみ（必須） |  | 現在、機密情報となる環境変数の定義はない。 |
| **環境依存値** | 環境変数（任意。デフォルト値を持つ） | `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_REGION`, `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_CLOUD_LOCATION`, `LLM_MODEL_AGENT`, `LLM_MODEL_TOOLS` | dev/stg/prod で異なる値を使用。デフォルト値により開発時の利便性を確保 |
| **アプリケーション設定** | コード定数 or 環境変数 | `DEFAULT_MODEL`, `MAX_AGENT_ITERATIONS` | ビジネスロジックやアプリケーション仕様に関わる固定値。将来的に柔軟性が必要な場合は環境変数化を検討 |

### チーム定義・プロンプト設定

* チーム定義（メンバー、プロンプト、トポロジー）は `configs/teams/` 配下に YAML ファイルとして一元管理する。
* プロンプトはチーム定義ファイル内にメンバーごとに記述する。同じ役割のメンバーでもチームによってプロンプトを変えられる柔軟性を重視する。
* チーム定義をコードから分離することで、コード変更なしに実験・比較が可能となる。

### 設計判断の指針

- **機密情報**: 必ず環境変数。例外なし
- **環境依存値**: 基本的に環境変数。`.env` + `python-dotenv` で管理し、必要な箇所で `os.environ` から参照する
- **チーム定義・プロンプト**: `configs/teams/` に YAML ファイルとして一元管理
